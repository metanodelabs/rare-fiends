# The toolkit this game is built on

**FriendSDK — `https://github.com/spokesz/friendsdk` — read at v0.1.2 — Apache-2.0.**

It is **not vendored**. There is no copy of it in this repository and no entry for it in any
`package.json`. It is a web address that was read once, and everything below depends on what was
read. That is the whole reason this file exists: if the repository moves, or `frames()` changes
shape, or a tag is re-cut, several milestones break and **no check would notice**.

### What `hardwired` actually decides

**This file used to say the opposite of the truth here**, and it was wrong in the dangerous
direction: it said the test "is true for every Friend, so it decides nothing." The mark is not inert.
It excludes most of the collection. Corrected 2026-09-30.

**The expression.** `src/identity.ts` line 26 at the pinned commit
`762d6f58a73ace723f7f82dc1a61bfa036c21edc`, fetched from the host on 2026-09-30 and read:

```ts
const hardwired = generation >= 1;
```

`generation` is whatever `generation(uint256 tokenId) view returns (uint8)` returns on the
Generations contract — the ABI is declared at the top of the same file, as
`GENERATION_ELIGIBILITY_ABI`. Three lines below, the same function returns `eligible`, which is
`ownedByPlayer && hardwired`. So `hardwired` is not a
trait and not artwork: a Friend starts at generation 0 and leaves 0 only when a holder **pays $RF to
hardwire it**. The collector reads that as the fee vault's `Hardwired(owner, tokenId, gen)` event,
with `Promoted(tokenId, gen, weight)` moving it afterwards. `hardwired` means **bought in**, not
**exists**.

**What share passes it.** Counted on 2026-09-30 from
`/Users/mostafakhader/Projects/rarefriends/data/state.json`, at `last_block` 76,296,165 — `gens_owner`
for who holds each Friend (a burn drops out), `gens_gen` for the generation the chain gave it, absence
meaning 0:

| | |
| --- | --- |
| Friends owned | **330,614** |
| at generation 0 — **not** hardwired | **268,289** — 81.15% |
| generation 1 to 6 — hardwired | **62,325** — **18.85%** |

The 62,325 spread across generations as 596 / 543 / 1,317 / 4,782 / 16,741 / 38,346 for generations
1 to 6. Every hardwired token id is also in `gens_owner`, so none of them is burned, and no stored
generation is 0 — the two stores agree and the two counts sum exactly to the total.

**That is a moving number, not a constant.** The collector is live and the file was last written at
01:20 on 2026-09-30. An earlier count on the same file gave 330,583 / 268,298 / 62,285; the three
differences are internally consistent with 31 new mints and 9 Friends hardwired in between. **So treat
the share — roughly one in five — as the fact, and the digits as true at that block.**

**Our contracts do not check it.** Grepped 2026-09-30: `RareChance.sol`, `RareCombat.sol`,
`RareDuel.sol`, `ShadowFriends.sol` and `test/Mocks.sol`. **No call to `generation(tokenId)` anywhere,
and the word `hardwired` appears in none of them.** `RareCombat` has a generation, but it arrives as a
`uint8` argument the caller supplies and `_gen()` only bounds it to 1–6; it never asks the NFT.
`ShadowFriends._ownerOf` is its own ERC-721 internal, not the Generations contract. So the toolkit
hands us a gate and **we currently use it nowhere.**

**The consequence, which is a decision to make and not a bug to fix.** If paid entry is ever meant to
require a hardwired Friend, that rule would exclude **about four in five owned Friends** — and
**nothing in our code would enforce it either way**, because nothing reads the value. The gate is
real, the number is large, and the choice is still open.

The tracker site's "hardwired" — in `template.html` and `v2/`, `v3/`, `v4/index.html` — is **the same
thing, not a coincidence of wording**: it counts exactly these paid `Hardwired` events. Those files
are the live token website and are read-only from here.

object to dereference. The GitHub API reports `"type":"commit"` for the ref, and `git ls-remote` shows
no `^{}` peeled line for it (nor for any of the four tags). So the hash above **is** the commit.

  `archived:false`, `fork:false`, default branch `main`.
- The licence is **Apache-2.0** at that exact commit, not just on the default branch: `LICENSE` is
  present in the pinned tree (blob `d645695673349e3947e8e5ae42332d0ac3164cd7`, 11,358 bytes, 202

```
git ls-remote https://github.com/spokesz/friendsdk refs/tags/v0.1.2
# expect: 762d6f58a73ace723f7f82dc1a61bfa036c21edc	refs/tags/v0.1.2

gh api repos/spokesz/friendsdk/git/ref/tags/v0.1.2 --jq '.object | .type, .sha'
# expect: commit, then the same SHA

gh api repos/spokesz/friendsdk --jq '{private, visibility, license: .license.spdx_id}'
# expect: private false, visibility public, licence Apache-2.0
```

If any of those three disagrees with what is written above, **the toolkit moved** — stop and find out
what changed before trusting anything in the table.

### We are two tags behind, and it does not currently matter

The repository has four tags: `v0.1.1` `0a6c5f8b…`, `v0.1.2` `762d6f58…` (ours), `v0.1.3`
`f34f4058…`, `v0.1.4` `ca3bf183…`. Diffing our pin against `v0.1.4` across the eight load-bearing
files above touches only two, and both changes are **purely additive**: an optional
`transferStartBlock` field on the sprite manifest and on `GenerationDeployment`. The registry address
is unchanged and `frames()` / `spriteFrame()` keep their shape. Re-read 2026-09-30: `FAMILIES_REGISTRY_ABI` is byte-identical between v0.1.2 and v0.1.4, so `portrait()` and `sceneFrames()` are unchanged too. `src/friend-sprites.ts` also changed, by a client swap (`createFriendReadClient`), which this section did not name before. So nothing we depend on has broken —
but that is a fact with a date on it, true as of 2026-09-29, not a standing guarantee.

### This is now a pin. It is still not a lock.

A commit hash fixes *which* bytes we mean; it does not give us those bytes. The hash alone still means
trusting the host, because:

- **Nothing fetches it, so nothing compares it.** No `package.json` entry, no submodule, no
  vendored copy — the hash is a sentence in a document, and no check in `estate/checkall.js` reads it.
  If the repository is deleted, renamed or made private, this file still looks correct.
- **A hash is falsifiable, not available.** GitHub cannot retroactively change a commit under a SHA,
  but it can stop serving it. A pin protects against substitution, never against disappearance.
- **We depend on files, not on a repository.** The table above lists ten things we use; they live in
  the eight files named in the last bullet under "The pin". The tree holds far more.

Closing that gap needs one of:

1. **Vendor the files we actually use** into this repository, with their blob hashes recorded, so the
   build never reaches the network. Smallest and strongest, and it makes the Apache-2.0 attribution
   obligation concrete rather than theoretical.
2. **A git submodule** at `762d6f58a73ace723f7f82dc1a61bfa036c21edc`, which at least makes the pin
   machine-checked instead of prose — but still fetches from the host.
3. **A checksum manifest** of the specific blobs we depend on plus a check that re-fetches and
   compares them. Cheapest to add, and the only option that would have caught a silent re-cut.

Until one of those exists, treat the table above as **read once, on 2026-09-29, and verifiable — not
guaranteed to still be there.**

**The attribution has to ship.** Apache-2.0, and this document says so twice. Nothing checks it
today; M22 adds the check.

## Before relying on anything above

Go and look. The design is explicit that what the toolkit already has "is something this agent has to
go and look at rather than something it can grep for", because none of it is on disk here. Two things
in this project were built twice for exactly that reason: our own crystal drawing when the toolkit
already had one, and sprite traits that are published and read for nothing but drawing.
